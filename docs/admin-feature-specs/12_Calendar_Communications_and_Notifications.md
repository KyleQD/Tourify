# Calendar, communications, inbox, and notifications

## Outcome

Provide a reliable organization/tour/event time view and a coherent communication layer. The calendar must aggregate canonical domain records and route edits through domain commands. Communications must target verified audiences, deliver through durable channels, expose failure/acknowledgement, and avoid duplicate or cross-tenant messages.

## Current baseline and gaps

- Calendar aggregates tours/events/tasks/shifts/production/hiring and supports ICS/feed-token concepts.
- Calendar code queries/inserts `org_id` on some staffing/logistics records inconsistently with audited migrations; direct calendar shift creation can omit venue/staff context.
- Multiple services resolve the first membership instead of active organization.
- Unified inbox, event groups, notifications, and Work Mode publication rows exist but do not share one audience/delivery/ack model.
- Request fanout and silent empty states make missing data appear as a legitimate empty calendar/inbox.
- Missing notification preference/consent, dedupe, escalation, provider failure visibility, and stable deep-link/correlation behavior.

## Calendar architecture

### Aggregated read model

Calendar items are projections with stable `sourceType`, `sourceId`, `sourceVersion`, `orgId`, tour/event/stop context, title, start/end, time zone, all-day semantics, status, owner, visibility class, deep link, and freshness. Sources include:

- tour stops and route/travel/rest days;
- event production windows/run-of-show milestones;
- travel, lodging check-in/out and transport pickup;
- staffing shifts, hiring/interview/onboarding deadlines;
- advances, logistics/vendor/contract/finance obligations;
- publication/acknowledgement deadlines.

Calendar does not directly insert heterogeneous source records. “Create shift/task/event/hold” opens or calls the canonical domain command with required context and validation.

### Feeds and export

- ICS export/download is a versioned authorized snapshot.
- Subscription feed token is hashed, scoped to org/user/filter/audience, expiring/rotatable/revocable, rate-limited, and access-logged.
- Feed content applies protected-field projection and uses stable UIDs/sequence/update/cancel semantics.

## Communications architecture

Use the publication/outbox infrastructure from document 04 for durable delivery. Communications add:

- channels/conversations scoped to organization, tour, event, department, incident, task, or named participants;
- message version, author/system source, audience, priority, protected-field class, attachments, reply/thread relation;
- inbox state (delivered/read/archived/muted) and action/acknowledgement where applicable;
- notification events generated by domain rules, user/org preferences, quiet hours, escalation, digest, and dedupe key;
- adapters for in-app first, then verified email/SMS/push integrations.

Do not treat chat delivery as proof of acknowledgement for safety-critical changes; use explicit acknowledgement records.

## Test requirements

- Time-zone/DST/all-day/range/recurrence, stable ICS UID/sequence/cancel, feed token expiry/revocation/projection, and source-degraded tests.
- Domain command preview/validation and conflict-overlay tests.
- Audience membership/revocation, dedupe, retry, provider failure, preference/consent, quiet hour, escalation and acknowledgement tests.
- E2E: create domain item → calendar projection → authorized edit → publish change → correct recipients receive/ack → feed updates.

## Deployment readiness

- Calendar never writes incomplete records directly and never hides source failure as empty state.
- All calendar/feed/message/attachment access honors active organization and source capability.
- Notifications are transactionally emitted, deduplicated, retryable, preference-aware, and observable.
- Critical actions use explicit versioned acknowledgement and escalation.
- Legacy fire-and-forget paths are disabled and delivery/read/ack definitions are consistent across the product.
