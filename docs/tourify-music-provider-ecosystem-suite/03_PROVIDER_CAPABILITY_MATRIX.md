# 03 — Provider Capability Matrix and Scope Boundaries

## Capability matrix

| Capability | Tourify Native | Audius | SoundCloud | Bandcamp |
|---|---:|---:|---:|---:|
| Search catalog | Full | API | API subject to access/terms | No general public catalog API assumed |
| Connect artist account | Native | Supported through Audius auth | OAuth 2.1 + PKCE | Approved API accounts only; otherwise link ownership workflow |
| Import metadata/reference | Full | Yes | Yes within permitted scope | User-supplied URL/embed metadata; approved API optional |
| Raw/native playback runtime | Yes | API stream resolution | Possible only where approved/permitted | No |
| Official embedded playback | Optional | Optional | SoundCloud Widget | Bandcamp embed |
| Mixed Tourify queue | Yes | Yes | Yes through widget/runtime adapter | Conditional; embed-runtime queue entries |
| Seek/progress precision | Full | Expected | Widget/API capability dependent | Embed capability dependent; may be limited |
| Offline access | Tourify policy | Provider terms | Prohibited for API content | Not a Tourify feature |
| Provider social actions | Native | Capability-driven | Limited and terms-driven | External links |
| Store/merch | Native marketplace | External/provider future | External links | Strong outbound storefront/merch role |
| Sales/fulfillment API | Native | Provider future | Not core scope | Only approved labels/fulfillment partners |

## Architecture consequence

The provider interface cannot pretend every provider supports the same operations. It must expose capabilities explicitly:

```ts
interface ProviderCapabilities {
  search: boolean
  accountConnection: 'none' | 'oauth' | 'link_verification' | 'partner_only'
  playback: 'native_audio' | 'resolved_stream' | 'widget' | 'embed' | 'external_only'
  preciseProgressEvents: boolean
  importMetadata: boolean
  playlists: 'read' | 'read_write' | 'none'
  commerce: 'native' | 'external_link' | 'partner_api' | 'none'
  backgroundSync: boolean
}
```

Generic UI checks capabilities before rendering controls. Unsupported actions are omitted, not allowed to fail after interaction.

## SoundCloud constraints that affect design

- OAuth uses OAuth 2.1 with PKCE and short-lived access tokens with refresh behavior.
- Direct stream requests are rate-limited per application; documented playback request capacity must be monitored.
- Offline access to API user content is prohibited.
- Display and playback require uploader and SoundCloud attribution plus a backlink to the relevant sound.
- Commercial use is constrained, especially around content not owned by the connected uploader.
- SoundCloud can change APIs and terms or revoke access; Widget mode is an important isolation/fallback path.

## Bandcamp constraints that affect design

- The official developer API is described for labels and merchandise fulfillment partners and requires contacting Bandcamp for access.
- The generally available integration path is the official embedded player generated by the artist/label.
- Tourify must not scrape pages to build a catalog or derive hidden stream URLs.
- Bandcamp is best modeled as both a music embed and a direct-support storefront source.

## Decision rules

1. Prefer the provider's official embed/widget when it reduces legal, rate-limit, or playback risk.
2. Use raw stream playback only when explicitly documented and approved.
3. Never emulate unsupported controls; show provider-specific limitations honestly.
4. Store canonical provider identifiers and links, not third-party audio.
5. Treat provider account connection and content ownership as separate concepts.
6. A user may link a release without proving account control, but verified ownership is required for management claims, privileged sync, or commerce configuration.

## Cross-cutting implementation guardrails

- **Audit first:** all file targets in this suite are candidates until confirmed against the live Tourify repository.
- **Additive only:** do not reset Supabase; do not drop, rename, truncate, or repurpose production columns or tables.
- **Preserve native playback:** Tourify-hosted audio remains a first-class provider and the fallback path.
- **Normalize at the boundary:** provider payloads are mapped into Tourify domain contracts before entering UI, queue, analytics, or persistence layers.
- **Resolve playback just in time:** expiring or provider-controlled playback URLs are never stored in Supabase, local storage, analytics, logs, or durable queues.
- **Feature-flag every provider:** discovery, connection, import, display, playback, sync, and commerce can be disabled independently.
- **Provider terms override product preference:** the common Tourify UX must adapt to each provider's permitted playback and attribution model.
- **No scraping:** do not scrape Bandcamp or SoundCloud pages, extract hidden stream URLs, bypass embeds, or reverse engineer provider controls.
- **Acting-account authorization:** all mutations must use Tourify's existing account/organization/artist authorization helpers.
- **Idempotency:** imports, links, syncs, analytics milestones, and webhook processing must be safe to retry.
- **Observability without leakage:** log request IDs, provider, operation, latency, and normalized error code; redact tokens, personal data, and playback URLs.
- **Rollback without data loss:** disable flags and detach provider execution paths; retain additive data for later recovery unless a user requests deletion.
