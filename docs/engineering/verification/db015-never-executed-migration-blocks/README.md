# DB-015 / CP-109 — migration blocks the ordered chain never executes

The detector is `scripts/ci/check-never-executed-migration-blocks.mjs`. This
directory holds everything that is not one of DB-015's two granted
`scripts/ci/` files: the report it generates, the harness that proves the report
against a real PostgreSQL, and this note.

## What is here

| Path | What it is |
| --- | --- |
| `report.json` | Generated by the detector. Do not hand-edit it: `execution-harness.sh` stage 8 regenerates it from the chain, and the detector's test asserts the report is byte-reproducible. |
| `execution-harness.sh` | The execution proof. Three throwaway PostgreSQL 16 clusters, the chain's own DDL extracted BY LINE RANGE at run time. |
| `README.md` | This file. |

DB-015's grant (CP-112) is two new `scripts/ci/` files with exact names plus a
`db015`-prefixed report under `docs/engineering/verification/`. `supabase/tests/`
belongs to WFC-004 this wave, so the harness is here rather than there, and it
says so in its own header. It READS `supabase/tests/db011_emulation_bootstrap.sql`
and writes nothing under `supabase/`.

## How to re-run

```bash
# the static path: no database, no credentials, seconds
node scripts/ci/check-never-executed-migration-blocks.mjs
node scripts/ci/check-never-executed-migration-blocks.mjs --json docs/engineering/verification/db015-never-executed-migration-blocks/report.json

# the sibling tests, which pin the properties the check is trusted for
node --test scripts/ci/check-never-executed-migration-blocks.test.mjs

# the execution proof: needs a local PostgreSQL 16, takes about a minute
bash docs/engineering/verification/db015-never-executed-migration-blocks/execution-harness.sh
```

The check is **not wired into `package.json` or `.github/workflows/ci.yml`.**
Those are outside DB-015's grant and the wiring is handed to release as
`HF-DB-015-CI-WIRING`. Until it is wired, the check runs on nobody's behalf —
which is the same position DB-014's sweep detector was in, and the same sentence
DB-014's task record used about it.

## The finding, in one paragraph

53 blocks in the active chain never execute. **One** of them is a high-severity
control that was believed in force and was not: `staff_performance_metrics`, the
instance CP-109 was written about, which DB-014 had already found and already
fixed at source. 13 are medium. 39 are low or informational, and the great
majority of those are defensive repairs and post-condition assertions that are
**correctly inert** — the block doing nothing is what it was written to do. The
class is real and it is a family of four spellings (`if exists`, `if not exists`,
`is null then return`, and `is null then null; else <control>`), it is not two
instances, and it is **narrower** than CP-109's framing implies. Both corrections
are in `report.json` under `correctionToCP109`.

The most useful thing found is not a new exposure. It is
`20250813122000_rls_tour_team_access.sql:98`, the one instance with a **measured
exposure window** behind it: its two scoped policies never ran, and the
permissive `tour_vendors_all` was therefore the only policy on `tour_vendors`
from 20250818121000 until 20260710032714 dropped it — three months. That is
CP-104's shape arriving through *ordering* rather than through a missing
successor, and it is the answer to "is this class worth a CI gate".

## What the detector is trusted for, and what it is not

Trusted for: reporting a guard-guarded block whose guard is false **at that
block's own version position**, with the block's intended objects named, and with
every finding resolved against a named owner and a severity.

Not trusted for, and never able to say: anything about a TARGET. A chain replay
cannot tell you what a database contains. DB-002 established that migrations have
been applied through the Management API, so a real target may differ from the
chain in either direction, and DB-013's migration ships anyway for exactly that
reason. Runtime-computed DDL, `execute format(...)`, and out-of-band application
are all invisible to any chain-only analysis. The full list is in
`report.json` under `limits`.

Both error directions are recorded in the report. A false positive is safe and
comes from out-of-band application, dynamic DDL, and this module's deliberate
bias of not crediting a `create table` found inside a guarded body. A **false
negative is the one that matters** and is guarded eight ways, the load-bearing
ones being: an unrecognised guard can only produce `unanalysed` and never
`clean`; there is no code path in the module that can emit the verdict `clean`;
and the CLI **refuses to report clean** unless it has actually found the two
instances CP-109 confirmed.

## The detector's own defects

`report.json` under `defectsFoundInThisDetector` records five defects this
detector had, each now pinned by a fixture. They are listed there rather than
only here because the reusable part is the failure mode:

1. a condition's polarity inferred from the presence of a `not exists` anywhere
   in it, which inverted every conjunction — four false positives in files whose
   names are security migrations;
2. only the `then` arm measured, so an inverted guard
   (`if X is null then null; else <control> end if`) reported the `null;` as a
   never-executed control — three `enable row level security` policies reported
   dead that are alive;
3. a `drop policy` block aimed at a policy no migration creates, reported HIGH
   because a quoted name with spaces was read as the next bare word — the policy
   named `on`, which the chain does create;
4. a `\s+` at the end of a keyword pattern eating the mask's blanks, the same
   capture from a second site;
5. the mask blanking every dollar-quoted span, so a DO body scanned through it
   contained nothing and **zero guard sites were found in the whole chain** — a
   clean report from a broken instrument, caught by the anti-vacuity gate before
   it could ship.

The general form: **each of them was a matcher slightly too loose, producing a
confident wrong answer, in the same direction as the answer the matcher was
supposed to replace.** They were found by running the thing against the real
chain, not by reading it, which is the whole argument of this task.
