## TICKET-006 checkpoint — 2026-09-27 (partial issuance, resume dedup, completion alert)

- **Durable fact — a ticket's issuance position is the unit of idempotency, not its existence.** `issueTicketsForOrder` used to return as soon as *any* ticket existed for an order, which both hid a partial issuance (a delivery that died after admission 1 left an order indistinguishable from a finished one) and lost the insert race outright. It is now per POSITION: every admission carries `issuance_slot`, and the database refuses a second admission for a filled position. The existence read survives only as an optimization, and it deliberately tolerates an unreadable read — inferring "nothing issued" from a read that failed is the unprovable inference the completion-marker fix removed.
- **Durable fact — "complete" is a proof, not a flag.** `ticket_sales.issuance_status` reaches `'issued'` only after a re-read proves every position is filled AND the admission count reaches the purchased quantity. Every failure before that proof — a database error, a *rejected* transport call, or a verification read that cannot be performed — records `'partial'` and rethrows. A `try/catch` guard flag (`verified`) keeps a post-proof failure from downgrading a genuinely complete order.
- **Durable fact — the resume repairs, it does not just retry.** The verification pass also creates a missing active credential, and the ownership audit row is written *before* the credential so an admission is never left unattributed. An admission whose slot is already filled can otherwise never be scanned, because the slot is taken.
- **Durable fact — `OptimizedNotificationService.createNotification` has NO idempotency handling.** The `idempotency_key` that `lib/ticketing/notifications.ts` puts in notification metadata dedupes nothing. Any "fire once" claim about a ticketing notification must be enforced by the caller, not by that field.
- **Durable fact — exactly-once for the completion alert is a compare-and-set on `ticket_sales.issuance_alerted_at`** requiring `issuance_status = 'issued'`, so it is unreachable for a partial issuance, cannot be won twice, and does not depend on in-process state. It is claimed immediately after issuance and *before* the remaining money writes, so a later ledger failure cannot leave a finished order unalerted. Bounded loss recorded: if the claim cannot be persisted, the alert is dropped rather than guessed at, because re-deriving "was this sent?" for an order issued before the column existed is unprovable.
