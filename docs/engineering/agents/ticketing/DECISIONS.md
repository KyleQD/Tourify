## DOMAIN-001 — A type-drift cluster is re-derived from source before it is acted on, and the disposition is per object, not per cluster

- Date: 2026-09-25
- Status: accepted
- Task: TICKET-005 (Wave 35), DB-008 ticketing code-drift cluster
- Decision: The four objects the inventory assigns to the ticketing cluster are dispositioned **individually**, each on its own re-derived evidence, and the cluster is not treated as a unit. For each object the lane first establishes whether the relation or RPC exists in the **active** migration chain, then re-derives the live consumer set by resolving real import specifiers from Next entry points (CP-066/CP-073), and only then chooses repoint or delete. A cluster that resolves to "no file in my grant" is recorded as a handoff with the exact `file:line` and a proven recipe, **not** as completed work. A **scoped** `tsc` A/B (the drifted read restored, then removed) is used to prove a diagnostic was real before claiming a reduction, and the reduction is always labelled scoped.
- Evidence: The inventory's file-level attributions did not survive re-derivation, in **both** directions. `track_venue_profile_view` was attributed to `app/api/ticketing/webhook/route.ts`, which contains no reference to it anywhere in the tree; the single real caller is `app/api/venues/[id]/route.ts:109`, a venue-domain path. `ticket_notifications` was recorded as `consumerVerdict: "dead"` with `lib/services/ticketing.service.ts` as an "unreachable module", but that module **is** live — `app/tickets/purchase/page.tsx` → `components/ticketing/ticket-purchase-form.tsx:14` → `import { ticketingService } from '@/lib/services/ticketing.service'`; only the *method* `sendTicketNotification` is dead, with exactly one occurrence in the repository, its own definition. `get_enhanced_artist_stats` has **zero** code callers: all eight occurrences are comments, one non-migration SQL file, and an archived migration, and the artist lane already pins this with `__tests__/artist/db008-code-drift-repoints.test.ts:241`. `settlements` was the only object with a real in-grant diagnostic, confirmed by A/B: with the read restored, `app/api/ticketing/settlements/route.ts:83` reports TS2589 plus two TS2769 overload failures — `Argument of type '"settlements"' is not assignable to parameter of type '"ticket_types" | ... | "world_track_places"'` — and with the read removed the file is clean.
- Consequences: One object was fixed here, one is already disposed by another lane, and three are handed off with corrected evidence; the lane's honest cluster reduction is 4 of 22 attributed hits in a single file, not a cluster cleared. The `settlements` fix **deletes a read rather than repointing it**, because the active chain contains no settlement relation and no settlement RPC to repoint to — `rg` over `supabase/migrations/` for any `*settle*` table or function returns nothing, and the canonical ticketing settlement surface is the pair the endpoint already reads, the append-only `financial_transactions` ledger and the versioned `ticket_revenue_allocations` waterfall. That mattered because the dead read's error was fused into the endpoint's availability gate, so on **every** deployment built from the active chain `GET /api/ticketing/settlements` returned 503 `ticketing_unavailable` and the authoritative money numbers never reached its one live client. The response keeps a `settlement: null` / `settlement_available: false` pair so an absent record is never readable as a zero or as a served record, and the availability gate still covers the two authoritative reads — the gate was **narrowed to the authoritative sources, not weakened**, and no money figure is now served from an unauthenticated or unverified read. `lib/database.types.ts` and all `types/**` were not touched, and the absence of a `settlements` entry in the generated union is itself the proof that the relation is gone from the type surface.

## DOMAIN-002 — "Not in the active chain" is not "not in the database", and a name in prose is not a consumer

- Date: 2026-09-27
- Status: accepted
- Task: TICKET-008, DB-008 ticketing code-drift cluster (disposition pass over DOMAIN-001)
- Decision: Two checks are mandatory before an object is called absent, and neither may be approximated by a text search. **(1) Schema resolution.** Every CREATE in the active chain is resolved to its *effective* schema by tracking each file's `search_path` at the statement offset, because an unqualified CREATE lands in the FIRST existing entry: `20260821025543` sets `search_path = private, public`, so `ticketing_migration_issues` is a `private`-schema relation. "Not in public" and "not in the chain" are different questions and the first is the wrong one to ask. **(2) Reference precision.** A consumer is a `.from('X')` / `.rpc('X')` argument in *executable* code — never a comment and never a log tag. Both false shapes are real in this cluster: the ticketing settlements route still names the relation in the comment that explains why it was removed, and still carries a `'[settlements] …'` log tag, so a substring scan reports a completed fix as a live consumer. A disposition may be `accepted debt` with a named decision owner; it may never be a guess, and a dead-consumer claim requires a stated zero-use method.
- Evidence: The schema resolver was wrong on its first run and the test caught it: it reported `ticketing_migration_issues` as `public` because it tested "is `public` anywhere in the path" instead of "is `public` the FIRST existing entry". After the fix it resolves `private`, and it independently finds `public.ticket_types`, `public.venue_profiles`, `public.ticket_revenue_allocations`, `public.financial_transactions` and `public.tickets`. The `private`-schema control is real, not hypothetical: it is a ticketing object, created by `20260821025543`, and it is invisible to any public-schema check. On reference precision, a first draft of the fence asserted a bare substring over the grant and failed against the settlements route on the comment and then on the log tag; both failures were in the test, not the product. Re-derivation also confirmed the reservation is a prohibition rather than a suggestion: `exec_sql` is created in no schema and its only repository SQL reference is a **revoke** in `20260717194541`, which is evidence the function must not exist — the fence now asserts it stays absent so "just create it" fails the suite instead of passing review.
- Consequences: The four objects are dispositioned with two dead-consumer and two accepted-debt outcomes, and the ticketing grant contributes 0 drift diagnostics (scoped tsc over `app/api/ticketing/**` + `lib/ticketing/**` names none of the four; the 15 remaining diagnostics are 9 pre-existing `enhanced/route.ts` TS2589/TS2769 on the same nine lines DOMAIN-001 recorded, plus 6 in `lib/services/optimized-notification-service.ts` pulled in transitively by `lib/ticketing/notifications.ts`, which is design-system's file and not a drift object). `settlements` is **accepted debt, not a dead consumer**: two live out-of-grant consumers remain and the chain itself records an out-of-band apply of the settlements tables (`20260720021441` is marker-only, body `select 1;;`, and its comment says "already applied via execute_sql"), so the repository holds both "the chain never creates it" and "some target has it" and only a catalog read on a real target decides — the same live-versus-chain shape DB-008 recorded for `scheduled_posts.platform_status`. New finding raised to venue: `lib/venue/finance-snapshot.ts:117` folds that unreadable read into a **false zero** (`settlementsRes.data || []` → every share reports `settlement_status: 'unsettled'`), so a venue is told money is unpaid when the truth is unavailable; the admin consumer of the same relation already fails closed, which is why the handoff is venue-only. The reservation on `ticket_notifications` is unchanged in substance but the deletion recipe is corrected: `getNotificationTitle` (384) and `getNotificationMessage` (398) are private and each occurs exactly twice, so deleting only 340-364 leaves two newly-dead private helpers. The fence lives in `__tests__/ticketing/db008-drift-cluster-disposition.test.ts` and is negative-controlled three ways — synthetic SQL proves the resolver fails on a resurrection in either schema order, synthetic sources prove a name in prose is not a consumer, and two live mutations of the settlements route (restoring the dead read, deleting `settlement_available: false`) fail 3 and 1 tests respectively, with the file restored to a byte-identical SHA. No migration was authored and none was applied (CP-051); TICKET-006's `20260927120000_ticketing_issuance_slot_dedup.sql` remains authored-only, so `issuance_slot`, `dedupe_key` and `issuance_alerted_at` are known-pending regeneration rather than drift.
