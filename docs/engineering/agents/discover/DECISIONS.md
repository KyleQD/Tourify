## DOMAIN-011 — The discover fan-out base origin is operator configuration, never the inbound request

- Date: 2026-09-25
- Status: accepted
- Task: DISC-002 (Wave 33, security lane)
- Decision: `/api/discover` aggregates four internal API routes over HTTP. The base origin of that fan-out is resolved only from server environment configuration — `INTERNAL_API_ORIGIN` first, then `NEXT_PUBLIC_APP_URL`, `VERCEL_PROJECT_PRODUCTION_URL`, `VERCEL_URL` — and it is matched as an **exact origin** (`scheme://host[:port]` after URL normalization), never as a prefix or substring. `request.url`, `Host`, and `X-Forwarded-Host` are never read for the destination. There is no localhost fallback: an environment with no allowlisted origin performs no outbound request and returns empty sections with one warning. Callers select an upstream by key from a frozen route map (`DISCOVER_UPSTREAM_ROUTES`), so no user value can become a host, port, scheme, or path segment; only length-bounded values passed through `URLSearchParams` reach the query string. Loopback or private origins are `local`-scoped and require both a non-production `NODE_ENV` and an explicit `DISCOVER_ALLOW_LOCAL_UPSTREAM=true`, so a production deployment cannot reach an internal address even if one is misconfigured.
- Evidence: CodeQL alert #16, `js/request-forgery` (security_severity_level critical, CWE-918) at `app/api/discover/route.ts:351` on `refs/pull/14/merge` at `5324399bf453f07d6a380bf6effab263383ff17c`, message "The URL of this request depends on a user-provided value." The taint source is `origin` from `new URL(request.url)` at line 328, which reflects the inbound `Host` / `X-Forwarded-Host` header; the sink was `fetch(`${origin}${path}`)`. The path component was separately tainted by the `location`, `creatorType`, and `service` query parameters, which were interpolated into the upstream URL.
- Consequences: `app/api/discover/route.ts` declares `export const runtime = 'nodejs'` because the transport uses `node:https` / `node:http` / `node:dns`. A deployment that sets none of the four environment variables loses the discover feed rather than silently proxying to a caller-chosen host; that is the intended fail-closed trade and release/infra must set `INTERNAL_API_ORIGIN` before this ships. `parseBoundedInt` replaces the previous `parseInt` in the `limit` handler, which produced `NaN` (and therefore a literal `limit=NaN` in the upstream query) for non-numeric input.

## DOMAIN-012 — The discover outbound transport resolves-then-pins and never follows a redirect

- Date: 2026-09-25
- Status: accepted
- Task: DISC-002 (Wave 33, security lane)
- Decision: The guarded internal fetch uses `node:https` / `node:http` directly rather than global `fetch`, and applies five independent barriers. (1) **Allowlist first:** the assembled URL is re-asserted against the exact-origin allowlist and a fixed path-prefix list before any socket is opened. (2) **Encoding normalization:** every host is classified as an IPv4 literal, IPv6 literal, or DNS name, and IPv4 is normalized through the historical `inet_aton` encodings (`127.1`, `0177.0.0.1`, `0x7f000001`, `2130706433`) before a numeric CIDR check; IPv6 unwraps the embedded IPv4 of `::ffff:0:0/96`, `::ffff:0:0:0/96`, `64:ff9b::/96` (NAT64) and `2002::/16` (6to4) before checking it. (3) **Resolve-then-pin:** all A/AAAA records are resolved, *every* record is range-checked, and the request connects to the validated address through a `lookup` override while `Host` and SNI stay on the allowlisted hostname — a mixed public/internal answer is rejected rather than pinned opportunistically. (4) **Structural redirect denial:** `node:https` does not follow redirects, and any 3xx is a hard denial, so an allowlist on the first hop cannot be bypassed through an open redirect on the upstream. (5) **Bounded cost:** a 5 s wall-clock timeout, a 2 MiB response cap enforced on both `content-length` and the streaming byte count, and a JSON content-type requirement so the endpoint cannot become an HTML exfiltration channel.
- Evidence: 40 tests in `__tests__/discover/discover-ssrf.test.ts` mock `node:https`, `node:http`, and `node:dns/promises`. Every rejection path asserts `httpsRequest.mock.calls.length + httpRequest.mock.calls.length === 0` — a denial must not reach the network sink. The redirect test emits a `302` with `Location: http://169.254.169.254/latest/meta-data/` and asserts exactly one hop was issued and that the request path never contained the redirect target.
- Consequences: The guard is deliberately reusable and has been handed off, unmodified, for the two unflagged siblings of the same defect class (`HF-DISC-002-HUB-SELF-FETCH-SSRF`, `HF-DISC-002-NEWSELF-FETCH-SSRF`). `app/api/hub/route.ts:82` and `lib/news/feed-service.ts:673` both build their outbound base from `request.nextUrl.origin` and were **not** flagged by CodeQL, because `js/request-forgery` treats `request.url` as a remote-flow source but not `request.nextUrl.origin`. A clean CodeQL run is therefore not evidence that those two are safe. This transport is also the reference implementation for the older `lib/marketplace/external-import.ts` guard, which validates hostnames by regex only and does not resolve or pin; that file was not modified and is out of this lane's ownership.

## DOMAIN-014 — The guard is one module: a new fan-out extends the frozen route map, it does not get a second transport

- Date: 2026-09-25
- Status: accepted
- Task: DISC-002 (Wave 34, security lane)
- Decision: `lib/discover/outbound-guard.ts` (pure) and `lib/discover/internal-json-fetch.ts` (resolve-then-pin) are the single outbound trust boundary for every discover-charter fan-out. A new fan-out adds frozen entries to `INTERNAL_UPSTREAM_ROUTES` — `HUB_UPSTREAM_ROUTES` for `/api/hub`, `NEWS_UPSTREAM_ROUTES` for the news RSS fan-out — and calls `fetchInternalJson` by key. It does not get its own allowlist, its own redirect policy, or its own transport. `ALLOWED_PATH_PREFIXES` is derived from the union of the frozen maps, so the path cross-check stays a restatement of the map rather than a second hand-maintained list. `DISCOVER_UPSTREAM_ROUTES` is left byte-identical so the Wave 33 tests that assert its exact pathname list keep meaning what they meant.
- Evidence: The hub previously used global `fetch` with no redirect, timeout, size, or content-type control; the news fan-out used global `fetch` inside a `categories.map`, so a single request controlled N concurrent server-side requests. Both are now the same transport as `/api/discover`. 25 tests in `__tests__/discover/hub-news-self-fetch-ssrf.test.ts` cover the three hub keys and the one news key, including source-text regression guards that strip comments before matching so the prose documenting the removed pattern cannot satisfy them.
- Consequences: The pathname union is now wider than one route's needs. That is deliberate and safe: the pathname is a compile-time constant chosen by key, so a caller can only ever reach a query parameter. The hub also forwards the caller's `Cookie` header (bounded to 8 KiB) because its three upstreams are session-aware — safe only because the destination is operator-allowlisted, which is the whole point of the rule. `app/api/hub/route.ts` gains `export const runtime = 'nodejs'`.

## DOMAIN-015 — A request-derived value is severed at the service boundary, not at the route that supplies it

- Date: 2026-09-25
- Status: accepted
- Task: DISC-002 (Wave 34, security lane)
- Decision: When the tainted value enters a module this lane owns and the routes that supply it do not, the property is retained as an optional, explicitly `@deprecated`, **unread** field with the reason documented inline, rather than deleting it and breaking out-of-lane callers. `BuildNewsFeedParams.requestOrigin` is now optional, documented as ignored, and read by nothing; the taint path ends at the service boundary. The two call sites that still pass it (`app/api/news/feed/route.ts:83`, `app/api/feed/for-you/route.ts:27`) keep compiling and are named in `HF-DISC-002-NEWSELF-FETCH-SSRF` for the property's removal.
- Evidence: Deleting the field outright would have been an excess-property-check compile error in two files owned by other lanes, on a shared dirty worktree with six concurrent lanes. A silently-ignored field is a footgun; a documented-ignored field is a visible debt with an owner. The test asserts the field declaration is the *only* remaining mention of `requestOrigin` in the file, so it cannot quietly start being read again.
- Consequences: Two out-of-lane call sites still put a request-derived origin on the wire into the service. It is inert, but it is not gone, and the task record says so rather than claiming the path is fully severed at the route.

## DOMAIN-016 — Plain-text conversion for untrusted values is decode-then-strip in one shared helper, with a residual-delimiter pass

- Date: 2026-09-25
- Status: accepted
- Task: DISC-002 (Wave 34, security lane)
- Decision: Third-party news values are converted for display by one helper, `lib/news/text-sanitize.ts` `toPlainText`, which (1) decodes entities in a **single semicolon-terminated pass**, (2) strips markup second, and (3) removes any residual `<` / `>`. Step 1 in one pass is what prevents `&amp;lt;` from decoding to `<` (the `js/double-escaping` half of the finding); step 3 is what closes the case a paired-tag regex structurally cannot, an unpaired `&lt;script` that decodes to `<script` with no closing bracket. The helper covers named, decimal and hex entities well past the fixed subsets the old per-call-site regexes used, which is the `js/incomplete-multi-character-sanitization` half. It is a **plain-text** conversion, not an HTML sanitizer: a value that must be rendered as HTML still needs a maintained allowlist sanitizer. `normalizeExternalHttpUrl` in the same module requires an absolute `http:`/`https:` URL and rejects `javascript:`, `data:`, `vbscript:`, `file:`, `blob:`, `about:`, protocol-relative, relative, credential-bearing, control-character-bearing and over-long values.
- Evidence: 17 tests in `__tests__/news/text-sanitize.test.ts`, including the exact payload the Wave 33 dispositions specified (`&lt;script&gt;alert(1)&lt;/script&gt;` → inert text) and nine further variants, with the invariant asserted directly: no input yields a string containing `<` or `>`. Alert #43's call site (`components/feed/rss-news-item.tsx`) is converted and its unvalidated `window.open(item.link, …)` is closed in the same change.
- Consequences: A sanitizer defect is fixed once, at the ordering, rather than five times as five regexes. The residual risk the Wave 33 disposition recorded — an unvalidated third-party `item.link` reaching `window.open`, which is a browser-side concern no CodeQL alert covered — is closed, and the Read and Share controls are disabled when the link is unusable rather than silently doing nothing.
