## DOMAIN-034 — A credential-adjacent drift cluster is classified by reachability and by error handling, not by object name

- Date: 2026-09-25
- Status: accepted
- Task: ADMIN-003 (Wave 34)
- Decision: For the `auth-identity` verification family (`verification_requests`, `verification_documents`, `verification_badges`, `verification_criteria`, `verification_history`, `calculate_verification_score`, `channel_participants`, `get_verification_status`, `submit_verification_request`), the required determination is made per object in this order: (1) is the object reachable from an entry point; (2) if reachable, does the consumer check the error; (3) only then classify as fail-open, fail-closed, or silent-wrong-state. Object names are not evidence — `verification_documents` sounds credential-bearing and here it is unreachable code behind an unreachable component.
- Evidence: `lib/services/verification.service.ts` has exactly one importer in the repository, `components/verification/account-verification.tsx:5`, and that component has zero importers (searched the module path, the `verificationService` symbol, and `AccountVerification`; only the file itself and two documentation rows match). All 8 service consumers read `if (error) throw error` immediately after the call (lines 82/87, 99/103, 243 and every table read), so the PostgREST rejection surfaces as a throw, never as a default value. The one live verification surfaces in the product read `artist_profiles.verification_status`, `venue_profiles.verification_status` and `profiles.is_verified` — different tables, none of which is in this cluster. Exactly one defect in the cluster is not fail-closed: `lib/services/project-workspace.service.ts:488` awaits a `channel_participants` insert with no destructured error and no check, then continues into `logActivity`, so `acceptInvitation` reports success, writes an activity row claiming the join, and silently never enrolls the collaborator in the project channel.
- Consequences: No migration is authored and the schema is not resurrected; the correct disposition is deletion of the unreachable island, because re-creating `verification_*` tables would revive a retired credential-adjacent surface with no owner and no RLS story. The `project-workspace.service.ts` error-discard is a real bug independent of the drift and is escalated with the exact line. Corrected one inventory error: `lib/services/venue.service.ts` is NOT a `submit_verification_request` consumer — it references only `verification_status` at line 213, a `venue_profiles` column. Routed to the design-system lane in `HF-ADMIN-034-AUTH-IDENTITY-VERIFICATION-CLUSTER`; the admin lane changed no file in this cluster. Fail-closed is proved from source and the generated contract, not from an observed PostgREST response, and that limit is stated in the handoff rather than papered over.

## DOMAIN-035 — An untyped Supabase client is a drift-detection hole, so column lists for admin reads get pinned by test

- Date: 2026-09-25
- Status: accepted
- Task: ADMIN-003 (Wave 34)
- Decision: `withAdminCapability` types its handler's client as `any`, and `createServiceClient` calls `createClient` without a `Database` generic. Any column an admin route selects through either is invisible to `tsc`. Therefore, for an admin read that was repaired for column drift, pin the exact select string in a test against a hard-coded copy of the contract's column list, rather than relying on the compiler to catch a regression.
- Evidence: `lib/auth/api-auth.ts:280` declares `auth: { user: any; supabase: any; ... }`. `app/api/admin/tours/artists/route.ts` selected `display_name` and `primary_genres` from `profiles` and produced **zero** tsc diagnostics across the whole `admin` cluster's scoped run, while failing at PostgREST on every request; `app/api/admin/events/[id]/task-messages/route.ts` likewise selected `profiles.display_name` and type-checked clean. By contrast `app/api/admin/onboarding/add-existing-user/route.ts` uses the typed `createClient` from `@/lib/supabase/server` and its `profiles.phone` read produced the cluster's only 3 diagnostics. The same `any` also hid a second defect in `tours/artists` — `profiles.primary_genres`, which is absent from the chain and from the contract, so repairing `display_name` alone would have left the route just as broken.
- Consequences: `__tests__/admin/admin-profile-column-drift.test.ts` carries the `profiles` column list as a literal, asserts the premise (`display_name` and `phone` absent, `show_phone` present as a boolean), and asserts every selected, `ilike`d and `ordered` column against it. The local `DirectoryArtistRow` / `ArtistGenreRow` interfaces make the projection explicit at the call site. The durable rule for the lane: a `tsc` error count is a lower bound on drift, never an upper bound, and an admin read reached through an `any` client is unverified until a test pins its columns.

## DOMAIN-037 — A drift repair never widens the row scope, even when the drift is in a globally readable query

- Date: 2026-09-25
- Status: accepted
- Task: ADMIN-003 (Wave 34)
- Decision: When repairing a column-drift defect in a query, the repair changes columns and nothing else. It does not add a tenant predicate, and it does not remove one that was not asked about — even when the surrounding query is visibly cross-tenant. The cross-tenant observation is recorded as an ADMIN-003 finding with evidence instead of being fixed in the same pass.
- Evidence: The `tours/artists` directory branch selects from `profiles` with `role = 'artist'` and no organization predicate, under a `tour.view` capability. That is a platform-wide directory read behind an organization-scoped capability, which is a genuine ADMIN-003 question. Tightening it would change who can search the artist directory and is a product decision; the comparable admin artist directory in `app/api/admin/artists/route.ts` solves the same problem with `organization_artist_members`, so the destination is known but the migration is not mine to make in a drift pass. The drift repair itself (`display_name` → `full_name`, `primary_genres` → `artist_profiles.genres`) deliberately preserves the exact row scope, the response shape, the `tour.view` guard and the limit clamp.
- Consequences: The cross-tenant read stays visible in the code and in this record rather than being resolved as a side effect, and the next ADMIN-003 batch can pick it up as a first-class item with the `organization_artist_members` precedent already named. The general rule for the lane: a drift repair is a correctness repair, and mixing it with a scope decision makes the diff unreviewable for both purposes.

## DOMAIN-038 — A user-search picker is bound to the acting organization's workforce directory, and paying that debt lowers a pinned admitted-gap count

- Date: 2026-09-27
- Status: accepted
- Task: ADMIN-020 (ADMIN-016 finding F2)
- Decision: `GET /api/admin/users/search` keeps its user principal and gains an organization bound taken only from `admin.orgId`; the caller may not name an organization. The visible id set is the canonical organization workforce directory — `listWorkforcePeople({ employerEntityType: 'organization', employerEntityId: admin.orgId })`, the same service `GET /api/admin/workforce/people` uses — and that id list is pushed into the `profiles` query as `.in('id', ...)` in 100-id chunks, so the scope is a query predicate rather than a filter applied after a platform-wide read. The registry entry moves from `resourceBoundary: none_recorded` to `{ kind: 'acting_organization', boundBy: ['admin.orgId'], verifiedAt: 'admin.orgId' }`, and the ADMIN-016 admitted-gap baseline consequently falls from 49 to 48. Two consequences are accepted explicitly rather than absorbed: the picker can no longer discover a platform user the organization has never attached, and a directory above `listWorkforcePeople`'s 500-person cap is truncated. Neither is repaired here.
- Evidence: The defect was a capability-only guard over an unscoped read — `withAdminCapability('workforce.manage')` followed by `select('id, full_name, email, avatar_url').or('full_name.ilike.%q%,email.ilike.%q%')` on `profiles`, which is platform-wide and publicly readable (`profiles_select ... USING (true)`), returning user **email**. The org-bound path was chosen over removing the route from the launch surface on three pieces of code evidence: the route is mounted by five live admin pickers, two of which are P0 security surfaces (`components/admin/rbac-role-assignment.tsx:63` for org role assignment and `components/admin/staff-roster-panel.tsx:88` for the org staff roster); the registry classifies it `capability_gated`, not `legacy_pending_migration`, so it is declared launch surface rather than admitted debt; and no migration is required because the acting-admin context already carries a verified organization and the directory service already exists. The base-SHA source contains no occurrence of `admin.orgId` and no `.in(`, so the base behaviour is provable rather than assumed. `lib/services/admin-workforce-people.service.ts` gates every branch on a non-null `employerEntityId`, so a collaborator or platform context with no organization returns zero rows instead of a global read. `__tests__/admin/admin-user-search-org-scope.test.ts` holds 21 tests, and **11 of them fail when the route is reverted to its base source** — observed, then reverted byte-exactly — so the cross-tenant denial is not a hardcoded literal over a now-false claim.
- Consequences: The count reconciliation is the part future lanes must copy rather than repeat as folklore. `routesWithoutResourceBoundary` is machine-enforced from two opposite directions — the registry's own `none_recorded` count, and `routeFiles - routesWithoutResourceBoundary` routes whose `verifiedAt`/`boundBy` markers are present in real source — so it is not a number a harness edit can satisfy. Reverting this route's boundary to `none_recorded` turns the proof red with `expected 49 to be 48` and `expected 242 to be 243`; keeping the boundary over the unbound base route turns it red with `verifiedAt "admin.orgId" is not present in the route source`. **Paying admitted debt legitimately lowers a pinned baseline; the only forbidden move is editing the proof harness to make a count pass.** Two smaller rules ride along: reject `org_id`/`ops_org_id`/`organizer_account_id` with `organization_scope_field_rejected` rather than silently ignoring them, so a caller that believes it is scoping the request gets told it is not; and correct a stale route-level `capability` projection when the code-exact `capabilityByMethod` already disagrees with it, provided no runtime consumer reads it (`ADMIN_API_ROUTE_REGISTRY` is imported by no other module today — re-check that before repeating the move). The accepted scope reduction is a product decision, not a defect: `components/admin/grant-tour-admins-panel.tsx` can no longer name an external collaborator as a tour admin, and that panel already carries a share-link invitation path for the non-`in_app` channel. Generalizable form of the decision: for an admin picker, the visible set is the organization's own directory, and a capability never substitutes for a tenant predicate.

## DOMAIN-041 — Two lanes may not move the same pinned figure concurrently, so the proof-harness lease is serialized and the count is an inter-task dependency

- Date: 2026-09-28
- Status: accepted
- Task: ADMWORK-001 (granted), ADMCOM-001 (deliberately not granted)
- Decision: `__tests__/admin/admin-registry-guard-proof.test.ts` is granted to `admin-workforce` for **ADMWORK-001 only**, bounded to the `routesWithoutResourceBoundary` figure (pinned at 48) for exactly three named routes, all of which currently declare `resourceBoundary: { kind: "none_recorded" }` in `lib/admin/route-registry/workforce.ts:180,195,495`, so the expected movement is **48 to 45**. `ADMCOM-001` is **not** granted the lease and is serialized behind ADMWORK-001. The DOMAIN-040 lease is discharged: ADMIN-022 is complete and its obligation to return the path to governance has been observed.
- Evidence: The collision is arithmetic, not procedural. Any task that converts a `none_recorded` boundary into a source-proven one necessarily decrements the pinned `routesWithoutResourceBoundary` count, because the proof is machine-enforced from both directions (the registry's own `none_recorded` set, and `routeFiles - routesWithoutResourceBoundary` routes whose `verifiedAt`/`boundBy` markers must be present in real source). Both ADMCOM-001 and ADMWORK-001 therefore edit the same number, and two lanes measuring the same count in one worktree will disagree at least once and one of them will "correct" the other. The three ADMWORK-001 routes were confirmed to be `none_recorded` by reading `lib/admin/route-registry/workforce.ts` directly, and ADMWORK-001's working set is otherwise correct and self-contained in its own segment.
- **A working-set defect in ADMCOM-001 was found by the orchestrator before activation, and it is the more interesting finding.** The record declares `lib/admin/route-registry/commerce.ts`, which resolves cleanly to `admin-commerce` and would have passed the segment check — but the vendor dashboard's registry entry is not there. It is at `lib/admin/route-registry/logistics.ts:941`, in **admin-logistics**' segment, with `authClass: "legacy_pending_migration"` and `resourceBoundary: { kind: "none_recorded", boundaryOwner: "ops-logistics" }`. So the task would have edited a fragment that does not contain its route while being unable to touch the one that does. The reason this was invisible: `control-plane-validation.mjs:275-289` only runs the segment check against **active** tasks, so a blocked record can carry a working set that would be rejected the moment it is activated. The route file itself is correctly a `shared:` entry owned by `admin-commerce` ("Vendor administration belongs to commerce even though this legacy route is nested under logistics"), so the segment assignment is deliberate and the *fragment* declaration is simply the error. ADMCOM-001 needs a corrected working set plus a lease on `logistics.ts`, and it is recorded blocked on that decision rather than being quietly re-pointed.
- Consequences: The generalizable rule is that **a pinned count is a shared resource, and two tasks that move it are a collision even when their file sets are disjoint.** Path-disjointness is necessary but not sufficient for collision-free dispatch; the correct test is whether two lanes write the same machine-enforced figure. The second rule is that **a blocked task's working set is unvalidated, so it is a hypothesis.** The control plane's segment check is an activation-time gate, not a creation-time gate, which means a record can sit blocked for a long time holding a working set that no longer reflects reality — and the longer it sits, the more confidently the mistake will be repeated in a dispatch brief. The standing obligation to return this path to `admin-governance` after each lease is now on its third holder, which is the cost of the pattern; if a fourth lane needs it, the correct response is to **split the proof harness per segment** rather than to add a fourth lease. That is a real piece of deferred work, not a hypothetical, and it belongs to `ADMIN-025` (admin-governance) rather than to whichever lane happens to need it next.
