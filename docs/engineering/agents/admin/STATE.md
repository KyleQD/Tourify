## Department scope in the admin capability system — 2026-09-26 (ADMIN-012, CP-094)

- **CP-094 is now expressible.** `department` is a first-class `AdminCapabilityTarget` scope. `ADMIN_CAPABILITY_TARGET_TYPES` (`lib/auth/admin-capabilities.ts:199-206`) is the single catalog, and both `AdminCapabilityTarget` (`:227`) and `EntityCapabilityGrant.scopeType` (`:223`) derive their type from it instead of repeating a string union. `isAdminCapabilityTargetType` (`:214`) is the runtime guard.
- **There is exactly one decision point that switches on the target type, and it is exhaustive.** `grantCoversCapabilityTarget` (`:255-296`) replaced the two inline string comparisons that used to live inside the `resolveEffectiveAdminCapabilities` grant filter. Its switch covers every catalog member and its `default` arm both fails `tsc` (`const unhandled: never = scopeType`) and denies at runtime. This was proven, not asserted: temporarily adding a seventh scope type with no switch arm makes the scoped `tsc` fail with `TS2322: Type '"vendor_department"' is not assignable to type 'never'` at `:292`. An out-of-catalog *target* is denied with `unknown_target_type` and is deliberately NOT normalized to "no target" — normalizing it would have let an organization grant authorize a resource it never named, which is the fail-open shape this task exists to remove.
- **The resolution rule, in full.** `departmentScopeDenial` (`:372-391`) returns a reason or null, and every branch fails closed. For a capability the role holds department-scoped: a target is required → the target type must be a known scope type → it must be `department` → the acting `orgId` and `userId` must both be known → a `DepartmentAuthorityInput` must be supplied → its `organizationId` must equal the acting `orgId` → its `userId` must equal the acting `userId` → the target department id must be in `managedDepartmentIds`. Nine denial codes are exported so a caller can report why rather than only that.
- **Secondary membership cannot reach authority, structurally.** `DepartmentAuthorityInput` (`:346-354`) carries `membershipDepartmentIds` so callers can pass what they have, and the resolver never reads it. That is enforced by a test, not by a comment, and it is why the rule survives a future refactor: there is no code path from a membership id to an allow.
- **The filter runs after the SEC-102 union, so a grant cannot re-widen the role.** `resolveEffectiveAdminCapabilities` applies `DEPARTMENT_SCOPED_ROLE_CAPABILITIES` at `:481-487`, after `base ∪ grantCaps`.
