## CP-051 — All SQL migrations are applied manually; never reset the database

- Date: 2026-09-09
- Status: accepted
- Task: ORCH-001 / DB-003 / DB-004 / cross-cutting (all agents)
- Decision: Every SQL migration is applied manually and explicitly — reviewed, one migration (or reviewed batch) at a time, via `supabase migration up`, targeted `db push`, or explicit psql apply — and never through a destructive or automated full-chain replay. `supabase db reset`, `db push --include-all`, forced replays, and any command that drops/recreates the database are forbidden. Local stack boot (`supabase start`) must not be treated as the migration application mechanism when it auto-replays the chain; if the stack applies migrations on boot, migrations must first be confirmed safe to apply in order, and any migration that fails (e.g. `pg_read_file` permission denial on the local stack) is filed as a manual-apply item, not automated around.
- Reason: A local `supabase start` auto-replay failed mid-chain on `20260415210006_signup_profile_and_email_confirmation.sql` (permission denied for function pg_read_file) after partially applying earlier migrations. Destructive replays risk losing live state and mask migration-order defects; manual application keeps every applied migration attributable, reviewable, and additive.
- Consequence: DB-003/DB-004 verification uses live-schema queries (table counts via SQL) instead of reset-based reconciliation; targeted RLS probes run against migrations applied manually; blocks are recorded as manual-apply items instead of being reset around.

## CP-058 — Interaction and notification reads never rely on service-role access

- Date: 2026-09-25
- Status: accepted
- Task: SOCIAL-007 (`SIM-20260922-SOC-003`)
- Decision: Social interaction and notification read paths must not use a service-role client as their read path. Every interaction and notification read runs on the caller-scoped client returned by `checkAuth` / `parseAuthFromCookies`, so the caller's own RLS applies (bearer and cookie session parity is required; a Bearer-only read model is not acceptable). Because the shipped migration chain gives `post_likes` and `post_comments` a permissive `USING (true)` SELECT policy, the application-layer post-visibility gate (`lib/feed/post-comment-access.ts` → `canViewPostComments`) is the **enforcement boundary** for those two tables, not a nicety: it must run before any interaction read, it must be fail-closed on error, and it must answer with the same 404 for a missing post and a non-entitled post so it is never an existence oracle. Per-user engagement aggregates are self-only — a caller-supplied `userId` that is not the authenticated identity is refused rather than resolved. Where a service-role read is genuinely required (cross-account fanout, admin analytics), the server must verify scope against the authenticated identity first, and the response must not disclose another user's private activity.
- Reason: `GET /api/notifications/social` accepted `?postId=` / `?userId=` and resolved them through the RLS-bypassing service client, so any authenticated bearer user could read likes, comments and shares of a followers-only or private post and any user's engagement counters. The Bearer-only auth model also denied web cookie clients while leaving the unscoped read open. Restoring the RLS-enforced client alone would not have been sufficient for likes/comments, and service role alone would have been insufficient for shares.
- Consequences: `GET /api/notifications/social` and `GET /api/posts/[id]/poll/vote` are gated and no longer service-role reads. `sharesReceived` on the self-stats response is now computed only from share rows the caller may read, so it can never count another actor's share; `posts.shares_count` is the aggregate surface for share totals. Tightening `post_likes` / `post_comments` SELECT policy is a database-lane change with client-side blast radius and is tracked as `HF-DB-006-SOCIAL-007` rather than authored here.

## CP-059 — Storage-owned relations: ask the server, do not re-derive its permission check

- Date: 2026-09-25
- Status: accepted
- Task: DB-008 (Wave 32)
- Decision: A migration that manages a relation owned by another role (the Supabase `storage` service owns `storage.objects` and `storage.buckets`) must not pre-check that permission by re-deriving it. It must attempt the privileged statement and let the server decide, absorbing the refusal so a fresh replay cannot be aborted by a boundary that has nothing to do with the migration's own subject. Each `CREATE POLICY` is attempted in its own subtransaction with a local `exception when others` handler, plus an outer backstop for the `pg_policies` existence reads. Skips are reported as `raise warning` carrying `sqlstate` and `sqlerrm`, never `raise notice`, because these migrations set `client_min_messages = warning` and a NOTICE-only guard fails invisibly. `create policy` remains inside a DO block, so the static duplicate-policy chain check does not attribute the name to a version, and the `pg_policies` existence check keeps the block idempotent.
- Reason: `CREATE POLICY` enforces `pg_class_ownercheck`, which the server satisfies for the exact owner, **a superuser, or any member of the owning role**. ## CP-063 — An SSRF fix is an exact-origin allowlist plus a transport that cannot follow a redirect

- Date: 2026-09-25
- Status: accepted
- Task: DISC-002 (Wave 33, discover section)
- Decision: A server route that fans out over HTTP to other routes of the same application resolves its base origin from operator configuration only (`INTERNAL_API_ORIGIN`, then `NEXT_PUBLIC_APP_URL`, `VERCEL_PROJECT_PRODUCTION_URL`, `VERCEL_URL`) and matches it as an **exact origin**; the inbound `Host` / `X-Forwarded-Host` / `request.url` is never a source for the destination, and there is no localhost fallback — an unconfigured environment makes no outbound request. Callers select destinations by key from a frozen route map, so no caller-supplied value can become a host, port, scheme, or path segment. The transport resolves all DNS records, range-checks **every** one of them after normalizing alternate IPv4 encodings and IPv4-embedded IPv6 forms, then pins the connection to the validated address. Redirects are not merely disabled: the transport does not follow them and treats any 3xx as a denial. Timeouts and response-size caps are mandatory so the endpoint cannot be used as a traffic amplifier. IP-literal and loopback origins are permitted only with a non-production `NODE_ENV` and an explicit opt-in.
- Reason: Alert #16 (`js/request-forgery`, critical, CWE-918) at `app/api/discover/route.ts:351` was a real vulnerability: the base was `new URL(request.url).origin`, which reflects the inbound host header, so a caller who could set `Host: 169.254.169.254` or an octal/decimal-encoded address reached internal services through the app's own egress. A single-hop allowlist checked *before* the request is not sufficient on its own — validate-then-resolve leaves a DNS-rebinding window between the check and the connect, and a default-following client makes an allowlist on hop 1 meaningless once hop 2 is an open redirect. Both gaps are closed by resolving first, pinning the connect, and making redirect-following structurally impossible rather than configuring it off.
- Consequences: `/api/discover` now returns empty sections and logs one warning in an environment with no allowlisted origin, which is a deliberate availability trade for fail-closed behaviour; release/infra must set `INTERNAL_API_ORIGIN`. Because the same defect class exists in `app/api/hub/route.ts:82` and `lib/news/feed-service.ts:673` and **CodeQL flagged neither** — the query treats `request.url` as a remote-flow source but not `request.nextUrl.origin` — a green CodeQL run is not evidence that a self-fetch is safe. Those two are routed in `HF-DISC-002-HUB-SELF-FETCH-SSRF` and `HF-DISC-002-NEWSELF-FETCH-SSRF` with the reference implementation. The older `lib/marketplace/external-import.ts` guard is validate-then-resolve with regex-only hostname checks and no IPv4/IPv6 normalization; it is out of discover's ownership and is named here as the next consumer to migrate.

## CP-070 — A drift measurement is a claim about an instrument, so the instrument is pinned before the claim is believed

- Date: 2026-09-26
- Status: accepted
- Task: DB-008 / DB-011 (Wave 34, database lane)
- Decision: When a database lane reports schema drift between the active chain and a generated contract, the report is a claim about the *measuring instrument* as much as about the schema, and the instrument is validated before the finding is acted on. Three requirements, all runnable:

- Status: accepted

## CP-080 — A claim is not a completion: a duplicate delivery is resolved by a completion marker the claimant writes, never by the uniqueness violation

- Date: 2026-09-25
- Status: accepted
- Task: TICKET-005 (Wave 35, ticketing lane) — disposition of `HF-INTG-006-TICKETING`
- Domain: ticketing, with `integrations` as the filing lane and `database` as the schema reviewer
- Decision: A claim-before-process webhook separates three outcomes, and the **uniqueness violation decides none of them**. `claimWebhookEvent` returns `{kind: 'claimed'}` or `{kind: 'duplicate'}`; a duplicate is then resolved by **reading a completion marker the handler itself writes after every side effect has succeeded**: completed → acknowledge the replay with zero side effects, claimed-but-not-completed → **resume**. An unreadable marker, a missing row, or an unwritable completion **throws or returns 500**, because "already handled" must never be concluded from a read that did not happen. The completion marker is a **new nullable column** (`completed_at`) rather than a relaxation of the existing claim stamp (`processed_at`), and historical rows are deliberately **not backfilled**: a pre-existing row has an unprovable outcome, and asserting it finished is the same unprovable claim that caused the defect. The same marker is written when the handler takes a deliberate no-op branch (unpaid session, unknown event type, unmatched order), because "finished with nothing to do" and "interrupted" are different states and collapsing them would either resume forever or acknowledge unfinished work.
- Reason: The integrations lane's P0 was structurally true, confirmed from source rather than accepted on summary: `20260821000000_reconcile_ticketing_foundation.sql:339-345` declares `processed_at timestamptz not null default now()`, which the claim INSERT stamps, so the ledger had **no field written at completion at all**; `claimWebhookEvent` returned a bare boolean; and the route answered `{received: true, duplicate: true}` on `false`. A paid order could therefore stay permanently unfinalized behind a success response after one transient error. Acknowledge-only was not an option: it is the defect. Resume was not free either — the repository already had the canonical shape for it in `app/api/photos/purchase/webhook/route.ts` (claim → read the marker → resume or acknowledge → **check the completion write**), and reusing that form is what made the fix auditable against an existing, working precedent rather than a new invention.
- Consequences: `20260926130000_ticketing_webhook_completion_marker.sql` adds `completed_at timestamptz`, `attempts integer NOT NULL DEFAULT 1`, and a partial index on the incomplete subset, with a planned manifest and a 17-case contract test; no RLS or policy changes, so the completion is writable only by the same service-role client that already claims the event. The route's response gains an additive `outcome` field (`processed` | `resumed` | `duplicate`) and never returns `duplicate: true` for work that did not occur. A 23505 alone is no longer treated as a duplicate unless the error is a genuine unique violation — the previous `message.includes('duplicate')` substring test was narrowed to `/duplicate key/i` so an unrelated fault cannot be silently classified as "already handled". **A dead `settlements` read was also removed from the same endpoint's sibling money route** (`app/api/ticketing/settlements/route.ts`): it targeted a relation the active chain never creates, so its error was fused into the availability gate and 503'd the authoritative money read on every deployment — see CP-081 for why the fix was removal plus an explicit unavailability marker rather than a loosening. The hosted half remains honestly blocked: no Stripe credential, no staging target, and the migration is authored only under CP-051, so the replay evidence INTG-006 acceptance criterion 2 needs is a `DB-008`/isolated-staging step.

## CP-081 — Turning "a retry is a no-op" into "a retry resumes" inverts the safety argument: every resumed side effect must be re-proved idempotent, and a status flag is not a receipt

- Date: 2026-09-25
- Status: accepted
- Task: TICKET-005 (Wave 35, ticketing lane)
- Domain: ticketing
- Decision: When a handler moves from "duplicate deliveries are acknowledged and do nothing" to "interrupted deliveries are resumed", the previous idempotency argument **no longer applies to the resumed path** and every side effect is re-audited under that new assumption. Three classes result, and each is handled by the class's own rule, not by one blanket guard: (a) side effects already guarded at the data boundary (`finalize_ticket_inventory` / `release_ticket_inventory` are status-guarded, `issueTicketsForOrder` returns the tickets an earlier attempt issued, `writeSaleLedger` / `writeRefundLedger` are absorbed by the partial unique `financial_transactions.idempotency_key` index, the referral mark is `.eq('is_used', false)`) run unconditionally on a resume, because skipping them would lose work; (b) side effects with **no per-order key** (`increment_promo_code_usage` is an unconditional counter) run **only on the delivery that performed the order's `pending → completed` transition**, discovered by returning the updated row instead of discarding the result — the bounded failure is one missed increment, and the unbounded alternative is a discount redeemed once per provider retry; (c) a **status flag is not a receipt**: `payment_status = 'completed' AND issuance_status = 'issued'` no longer short-circuits on its own, because a delivery that died after issuance but before the ledger write leaves an order that looks finalized and has **no revenue receipt at all**, so the guard verifies the receipt and otherwise falls through to the idempotent repair path. Every failure in this class is resolved **toward writing or toward retrying**, never toward acknowledging.
- Reason: This is the part a claim/complete split does not deliver on its own, and it was found by the new tests rather than by reading. The resumed delivery hit the `alreadyFinalized` guard and returned without writing the revenue receipt, so the test asserting a resume repairs the ledger observed `saleLedgerWrites: 0`. That receipt loss is **pre-existing** — under the old acknowledge-on-23505 behavior the same interrupted delivery also never posted the receipt — but the P0 fix is the first point at which a retry can actually repair it, and shipping resume without it would have traded "a paid order can be stuck unfinalized" for "a finalized paid order with no revenue receipt". Verifying the receipt is also the only reading of "already finalized" that is honest under a resume.
- Consequences: `finalizePaidOrder` gains `hasSaleLedgerReceipt`, which treats an **unreadable** receipt as **absent** rather than recorded, because the write it guards is idempotent while skipping it loses money and the asymmetry has to point at writing. The two pre-existing `refund-replay.test.ts` assertions that pinned the already-finalized call log to exactly `['from:ticket_sales']` were updated to include the `from:financial_transactions` **read**, with the note that a verification is not a side effect; no behavioural expectation changed. Three known residues are recorded rather than silently absorbed: a **partial issuance** (a delivery that dies between ticket 1 and ticket 2) is not repaired, because `issueTicketsForOrder` returns as soon as any ticket exists for the order, so the order stays `completed` with `issuance_status` unset and re-runs the repair path on every later replay; **analytics rows are not deduplicated**, because `ticket_analytics_events` has no unique key and adding one is a larger schema change than this defect warrants, so a resumed delivery can emit duplicate `checkout_completed` / `ticket_purchased` rows (metric inflation, not a ledger error); and `increment_promo_code_usage` is **not in the active chain at all**, so the guarded counter is currently inert and will only start mattering when that RPC is provisioned. All three are recorded in TICKET-005 as open items rather than claimed closed.

## CP-107 — A policy sweep that exempts by NAME is not a policy sweep, so the exemption is a permanent blind spot that is invisible in the migration text and a rename can silently disarm

- Date: 2026-09-26
- Status: accepted
- Task: DB-014
- Domain: database, security-admin, release, orchestrator
- Decision: `20260823210000_harden_hiring_onboarding_pii.sql:293-313` sweeps permissive policies off its `v_tables` list by inspecting `pg_policies` and dropping anything whose `qual` or `with_check` is `true` or matches `%auth.role()%authenticated%` — **except** policies whose name matches `%employer_manage%`, `%applicant%`, `%worker_read%`, `%pii%`, `%global_template%` or `%published%`. Those six name classes are therefore **permanently unsweepable**: a genuinely permissive `USING (true)` policy carrying any of those substrings survives every future run of that sweep, and the mechanism that would remove it is the mechanism that skips it. The exemption is not visible where a reader looks for it — it is six `and policyname not like` lines inside a `DO` block, not a property of the policies themselves. This is accepted as a durable design defect, not a one-table bug, and it is made detectable rather than fixed: `scripts/ci/check-sweep-exemption-hazard.mjs` (static, chain-anchored) and `supabase/tests/db014_sweep_exemption_permissive_policies.sql` (read-only, target-side) now enumerate permissive policies, decide whether each is independently scoped or merely an authentication test, and report every one that is both unscoped and exempt-by-name. The sweep's own exemption list is **extracted from the chain at run time** and required to be known to the detector, so a seventh exemption fails the check instead of silently creating a seventh blind spot.
- Reason: A security control that survives on its name is not a security control. It is disarmed by a rename, inherited by a new policy that happens to match, and — worst — it reads as *protected* to the person auditing it, because the name `staff_members_employer_manage_hiring` reads as "an employer-scoped policy" and the exemption list confirms the name is on the allow-list. The measured proof is in `supabase/tests/db014_sweep_exemption_hazard.harness.sh`, which runs the chain's own sweep block against a real catalog with two policies that differ **only by name**: it drops `job_applications_read` and keeps `job_applications_employer_manage_hiring`, both `USING (true)`. That is the hazard executed, not described. It is also the same failure family as CP-104 and CP-085 — a control that reads as a fix — with the specific twist that here the *absence* of a control is legible as the *presence* of one.
- Consequences: Three rules follow, and the first is the one that would have caught this lane's own mistake. **(1) Detection must be anchored to the chain, not to a hand-copied list.** The detector extracts every `policyname not like` in the active chain and fails if it does not know the pattern; CP-104's standing rule ("detection must be at least as tight as the most permissive sweep in the chain") is now a test rather than a sentence. **(2) An exemption is a claim about a policy's scope, so it must be checkable, and the only cheap check is structural.** A policy may be exempt-by-name only if its applicable clauses reference a recognised authority, tenancy or lifecycle construct. That is a *necessary*, not a sufficient, condition: it proves a policy is not merely an authentication test, and it cannot prove a policy is correctly scoped. Text analysis has exactly this resolution and no more; correct scoping is proven behaviourally. Both directions of the error are recorded — a scope built from an unrecognised construct is a false positive (annoying, safe) and a recognised construct that constrains nothing is a false negative (unsafe) — which is why the construct list is deliberately short and leads with the chain's own authority functions. **(3) `to service_role` unconditional policies are not an exposure class and a detector that reports them is worse than none.** `service_role` has `BYPASSRLS`, so 29 such policies in this chain grant nothing to `anon` or `authenticated` (DB-013's recorded judgement); reporting them buries the findings. Same reasoning retires `AS RESTRICTIVE` policies from this check's class, and same reasoning pins the `polcmd` carve-out: a `FOR INSERT` policy has no `USING` clause at all, so a null qual there is structural and must never be read as `USING (true)`. The detector is not wired into CI in this lane — `package.json` and the CI workflow are outside the database agent's grant — so it is handed to release/orchestrator as a two-line wiring job, and until it is wired it exists, is proven, and runs on nobody's behalf.

## CP-114 — An RLS-filtered write is a silent no-op, not a denial, so every workforce command must read the affected-row count and `not_authorized` must be derived from it

- Date: 2026-09-27
- Status: accepted
- Task: WFC-004
- Domain: database, work, admin, qa, orchestrator
- Decision: PostgreSQL applies a row-level policy by **filtering candidate rows**. A `DELETE`/`UPDATE` whose `WHERE` matches no row the caller may see affects **zero** rows and exits **0**. An `INSERT ... SELECT` whose own `SELECT` is RLS-filtered to zero rows inserts nothing and exits **0**. Only a `VALUES`-form `INSERT` always evaluates `WITH CHECK` and raises 42501. Therefore **no RLS-mediated write may report success from the absence of an exception**: the caller must read the affected-row count, and `not_authorized` must be produced from a count of 0.
- Reason: This was found by the WFC-004 harness asserting on the psql **exit code** and reporting two `rc=0` failures that were both *successes*: a worker whose only relationship to a department is a secondary membership ran `update workforce_departments set name='hijacked' where id = <dept>` and got exit 0, and the same caller inserted into the operational status ledger and got exit 0. Neither wrote anything. It is CP-110's plausible zero arriving through **row-level security** rather than through a capability gate, and it is worse than a denial in exactly the way CP-110 identified: a denial is legible and a zero is believed. A route that reports "saved" from a 0-row write will tell a department manager their change was applied when the database never saw it, and an administrator will read an empty department roster as an absence of people rather than an absence of authority. The proof that it is the policy and not a coincidence is a pair: the same statement affects **0** rows for a secondary-only member and **1** for an organization administrator, and the results differ only in who is asking. A related distinction is measured in the same harness: a relation can carry a **privilege without a policy** (`workforce_departments` DELETE — granted to `authenticated`, denied by the policy, 0 rows) or a **policy without a privilege** (`workforce_department_memberships` DELETE — no policy and no grant), and only checking both would tell a reader which control is doing the work.
- Consequences: `WFC-005`'s departments/memberships write commands must read the affected-row count, and `WFC-008` through `WFC-010` must derive `not_authorized` from the count rather than from an absent error. A command that reads a set and then writes it can report success having changed nothing, because the read was already RLS-filtered, so those commands count writes and not reads. `HF-WFC-004-AFFECTED-ROW-COUNT`. This also changes what a *correct* probe looks like against the WFC-004 schema: a secondary-only member's update affecting 0 rows and exiting 0 is the **expected** result and must not be "fixed" by adding a permissive policy — which is the exact historical repair this repository has been correcting since CP-104.

## CP-115 — A column-level boundary cannot live in an RLS `with check`, so the department UPDATE policy is symmetric and the protected columns are a trigger; both halves are asserted because either alone is a defect

- Date: 2026-09-27
- Status: accepted
- Task: WFC-004
- Domain: database, work, admin
- Decision: CP-094's resource scope for a department manager — *may edit the department they are accountable for, may not re-point its tenant or vendor binding* — is expressed by **two mechanisms, because no single one can carry it**. The `wfc004_workforce_departments_update` policy is **symmetric**: `using` and `with check` both admit organization-wide `workforce.manage` **or** `workforce_department_is_managed_by(auth.uid(), id)`. The same split is the right shape for any future WFC column-level boundary: **RLS answers "may this caller touch this row", a trigger answers "may this caller touch these columns"**, and putting the second question in the first place is the mistake.

## CP-129 — The application capability gate is a structural superset of the RLS matrix, and the split-brain is a false-denial inventory

## CP-130 — A capability that no RLS policy reads is a declared intent, and a matrix value for it is inert

- Date: 2026-09-28
- Status: accepted
- Task: DB-017
- Domain: database, all implementation lanes
- Decision: Adopt a fourth disposition alongside matrix-authoritative, catalog-authoritative and deliberately-unseeded: **`declared_intent_only`**. A capability whose literal is passed to no enforcement site in the active chain constrains no row-level access, and any value for it in `org_role_permissions` is **inert** — it reads as authority in a table dump and grants nothing. Such a capability must be labelled as declared intent and must never be counted as enforced.
- Reason: 29 of the 42 capabilities in this repository are in this class, so a three-way classification silently forces them into one of the other three buckets, and each of those buckets carries an enforcement claim that is false. `workforce.publish` is the instance the class was written for: DB-016 seeded it into eight roles so the matrix would agree with the route gate, it is read by no policy, function or trigger anywhere in the 323-migration chain, and its only occurrence is a CHECK constraint that admits the value and authorizes nothing. `finance.manage` is a second, previously unrecorded instance: in the catalog, in the matrix for three roles since `20250816132000`, and read by nothing. With `finance.view`, `finance.approve`, `finance.pay` and `advance.manage` also unread, the chain enforces **no** finance capability at row level.
- Consequences: The class is not a label, it is a rule with teeth: a decision whose measured enforcement is weaker than it claims fails the check as the FALSE-NEGATIVE direction, and a new reader of a declared-intent capability fails it too, because a check that rewards being stale is not a check. Because the matrix is a superset of what RLS reads, the 9 inert matrix grants are an acceptable steady state and **removing them is a REMOVAL**, which DB-016's additivity rule forbids. The correct action is to label them and route the underlying question to the capability's owner.

## CP-131 — Enforcement must be classified by transitive reachability from a policy predicate, not by a grep of policy text

- Date: 2026-09-28
- Status: accepted
- Task: DB-017
- Domain: database, all implementation lanes
- Decision: Adopt as the method for classifying whether a capability is RLS-enforced: a capability is enforced **if and only if** its literal is passed to the matrix authority inside a statement that creates a policy, or inside a chain-defined function transitively reachable from such a policy. A statement that merely names a permission in prose, or a literal that appears only in an RPC guard, a trigger or a CHECK constraint, is not row-level enforcement and must be classified as such.
- Reason: The grep answer is wrong in the dangerous direction and this repository contains the proof. `logistics.view` and `logistics.manage` are read only through `private.user_can_read_staff_zone` / `user_can_edit_staff_zone` (`20260903120000:53500`, `:53568`) and appear in **no** `create policy` statement anywhere, so a policy-text grep reports both as constraining nothing. They are enforced. The converse also exists: `tour.publish` is enforced by three publication RPCs that call `has_perm` and then `RAISE`, and no policy reads it at all, so a policy-only instrument reports it as unenforced on a launch-critical publication path. `event.manage` shows a third shape.
- Consequences: Any RLS classification tool in this repository needs a **call graph**, not a text matcher, and a statement splitter that is correct on dollar-quoted bodies. Both of DB-017's own first-revision defects were in that machinery and **both produced a confident clean report**: a splitter that lost the second half of a file, and an argument extractor that found 41 of 42 capabilities constraining nothing while exiting 0 — the sixth consecutive instance in this repository of a revision passing while its instrument could not fail. The standing rule generalises: assert your own post-state, and check that the instrument can fail before believing that it did not. The count of policy sites is also not a count of policies.
